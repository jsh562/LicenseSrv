# Data Integrity Requirements Quality Checklist

> Purpose: A unit test for the SPEC/data-model of the signing service & key-custody registry — checks whether the requirements specify the `signing_key` schema, the one-active-key invariant, the status state machine, forced-RLS tenant isolation, the `product_keyring` view, and custody/audit integrity completely and consistently; it does not test running code.

**Created**: 2026-07-02 | **Feature**: [spec.md](../spec.md) | **Domain**: Data Integrity | **Audience**: PR reviewer

## signing_key Schema Completeness

- [X] CHK101 Are all required `signing_key` columns enumerated with type, nullability, and constraint — `id`, `tenant_id`, `product_id`, `key_id`, `algorithm`, `public_key`, `status`, `valid_from`, `valid_until`, `private_key_ref`, `custody_scheme`, `created_at`, `created_by` — and is the PK specified as composite `(tenant_id, id)` with a UUID v7 `id`? [Completeness, data-model §2] — Satisfied: §2 column table enumerates all 13 columns with type/nullability/constraint; §1/§2 give PK `(tenant_id, id)` and `id` = UUID v7.
- [X] CHK102 Are the validity-window columns' semantics defined — when `valid_from`/`valid_until` are set, the meaning of a null `valid_until` (open-ended trust), and their role as published verifier hints in the keyring — rather than left as bare nullable timestamps? [Clarity, data-model §2 / §5b] — Satisfied: §2 defines `valid_from` (set at activation), `valid_until` (null = open-ended trust) as published keyring verifier hints (TR-008); echoed in §5b projection.
- [X] CHK103 Is the `public_key` shape specified (32-byte Ed25519) with the length-guard CHECK clearly marked advisory/optional, and is the `algorithm` domain (`DEFAULT 'ed25519'`, free-text validated in the repository rather than a DB CHECK) and its rationale stated? [Clarity, data-model §2 / §4] — Satisfied: §2/§4 mark the `octet_length(public_key)=32` CHECK "optional/advisory" and state `algorithm DEFAULT 'ed25519'` as free text (repo-validated, no DB CHECK) so a future algorithm needs no migration.

## Private-Key Custody Integrity

- [X] CHK104 Is the invariant that NO column ever stores a plaintext private key stated as a hard requirement, with `private_key_ref` defined as only an envelope-wrapped blob (keystore) or an opaque backend handle (KMS/PKCS#11) — never key material readable back to a caller? [Completeness, Spec TR-010 / data-model §3] — Satisfied: §3 "No column ... ever holds an unwrapped private key" + Conventions bullet (TR-010); `private_key_ref` = wrapped blob or opaque handle, and the `Signer` has no key-read/export op so nothing reads it back to a caller.
- [X] CHK105 Is `custody_scheme` specified as the discriminator that determines how `private_key_ref` is interpreted (e.g. `keystore-aes256gcm-v1`, `kms-aws`, `pkcs11`, extensible free-text), and is `private_key_ref`'s nullability justified by scheme so a null/handle case is not mistaken for a missing-key integrity error? [Clarity, data-model §2 / §3] — RESOLVED: `custody_scheme` already the discriminator (§2/§3); added to §2 `private_key_ref` that presence-per-scheme is repo-validated (keystore = non-null wrapped blob; KMS/PKCS#11 = handle or null resolved from `key_id`), so a null handle case is a valid custody state, not a missing-key integrity error.

## Uniqueness & the One-Active-Key Invariant

- [X] CHK106 Is the one-active-key-per-product invariant specified with a concrete enforcement (partial unique index `ON signing_key (tenant_id, product_id) WHERE status='active'`) and its exact scope (per tenant + product), while rotating/retired/revoked rows remain unconstrained in count? [Completeness, data-model §4 / §6] — Satisfied: §4 partial UNIQUE `ON signing_key (tenant_id, product_id) WHERE status='active'` = exactly one active per (tenant, product); rotating/retired/revoked explicitly "unconstrained in count"; §6 confirms signing selection = {active}.
- [X] CHK107 Is `key_id` uniqueness scoped precisely to `UNIQUE (tenant_id, product_id, key_id)` — unique per product, not global — so a verifier resolves exactly one public key per `key_id` within a product? [Consistency, data-model §4 / §2] — Satisfied: §4/§2 specify `UNIQUE (tenant_id, product_id, key_id)` = unique per product (not global); "verifiers resolve one public key per `key_id`" (TR-003).

## Status State Machine

- [X] CHK108 Are ALL `status` transitions enumerated with their triggers — create→active, create→rotating, active→rotating, rotating→retired, any→revoked, retired→(row removed) — so no reachable transition is left undefined? [Coverage, data-model §6] — Satisfied: §6 table enumerates all six transitions (create→active, create→rotating, active→rotating, rotating→retired, active/rotating/retired→revoked, retired→row-removed) with triggers.
- [X] CHK109 Is `revoked` declared explicitly terminal (no `revoked→active`) and always-retained, and does the closed status CHECK domain `('active','rotating','retired','revoked')` match the state-machine table with no drift between the two? [Edge-Case, data-model §6 / §2] — Satisfied: §6 Rules declare `revoked` terminal ("no `revoked → active`") and always-retained; §2 CHECK domain `('active','rotating','retired','revoked')` matches the four states used in the §6 table.
- [X] CHK110 Are the two derived sets defined unambiguously — trusted/published = `{active, rotating, retired}` and signing-selected = `{active}` only — so keyring membership and active-key selection are each precisely specified rather than inferred? [Ambiguity, data-model §6 / §5b] — Satisfied: §6 Rules define trusted/published = `{active, rotating, retired}` and signing selection = `{active}` (exactly one/product); §5b restates the publication set.

## Rotation Overlap Window

- [X] CHK111 Are the rotation overlap window's DATA semantics specified — the prior key moves `active→rotating` and stays in the trusted/keyring set while exactly one new key becomes `active`, with the old-active flip and new-active insert required in the SAME transaction so the partial-unique invariant is never transiently violated? [Edge-Case, Spec TR-007 / plan HINT-003 / data-model §4] — Satisfied: §6 keeps prior key `active→rotating` and trusted for the overlap (TR-007); plan HINT-003 requires the old-active flip + new-active insert in the SAME transaction to avoid violating the partial-unique index.

## product_keyring View

- [X] CHK112 Is the `product_keyring` view's projection specified to include only public material (`key_id`, `algorithm`, `public_key`, `valid_from`, `valid_until`, `status`) and to EXCLUDE `private_key_ref` and `custody_scheme` on every path, so custody material cannot surface in JWKS output? [Completeness, data-model §5b / §3] — Satisfied: §5b view SELECTs only key_id/algorithm/public_key/valid_from/valid_until/status and states it "Never projects `private_key_ref` or `custody_scheme`" (also §3).
- [X] CHK113 Is the view's row filter specified as `status IN ('active','rotating','retired')` so revoked keys are omitted from the published keyring immediately, and is `security_invoker = true` required with its rationale (RLS evaluated as the invoking app role, not the owner)? [Consistency, data-model §5b / §6] — Satisfied: §5b view WHERE `status IN ('active','rotating','retired')` omits revoked immediately, and requires `security_invoker = true` with the "honor invoking role's RLS + app.current_tenant, not the owner's" rationale.

## Tenant Isolation (Forced RLS & Grants)

- [X] CHK114 Is the `tenant_isolation` policy predicate specified exactly — `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid` for BOTH `USING` and `WITH CHECK` — so an unset GUC matches zero rows (query refused) rather than running unscoped? [Clarity, data-model §5 / §5b] — Satisfied: §5 policy sets both `USING` and `WITH CHECK` to `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid`; unset GUC → NULL → matches zero rows (query refused, never unscoped).
- [X] CHK115 Are both `ENABLE` and `FORCE ROW LEVEL SECURITY` required (with FORCE's purpose — subject the owner too so an owner-owned view cannot bypass isolation — stated), and are the grants to the non-owner `licensesrv_app` role enumerated (`SELECT, INSERT, UPDATE, DELETE`) with justification for `UPDATE` (status transitions) and `DELETE` (removing a retired key only)? [Coverage, data-model §5] — Satisfied: §5 requires `ENABLE` + `FORCE ROW LEVEL SECURITY` (FORCE "subjects the owner too, so no owner-owned view/function can silently bypass"), grants `SELECT,INSERT,UPDATE,DELETE` to `licensesrv_app`, with UPDATE (transitions) and DELETE (retired-key removal only; revoked retained) justified.
