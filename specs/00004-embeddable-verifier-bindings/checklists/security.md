# Security Requirements-Quality Checklist: Embeddable Verifier Bindings

> Purpose: A "unit test for the spec" — these items probe whether the Security requirements are complete, clear, consistent, and testable, not whether the code behaves.

## Panic / UB Across the FFI Boundary

- [X] CHK001 Are requirements defined for what a panic inside the verifier core returns across the FFI boundary (a specific defined error code vs. undefined behavior)? [Completeness, Spec FR-005] — FR-005 + Plan AD-002 + Error Handling Strategy: `catch_unwind` at the boundary returns the reserved `Internal` code, never undefined behavior.
- [X] CHK002 Is the requirement that "no panic or UB may cross the FFI boundary" stated identically for every binding surface (C-ABI, WASM, UniFFI), or could it be read as C-ABI-only? [Consistency, Spec FR-005] — RESOLVED: extended FR-005 to state the no-panic/UB rule applies identically to C-ABI, WASM, and UniFFI surfaces, not the C-ABI alone.
- [X] CHK003 Is the reserved error code returned on a caught panic specified as a stable, documented value rather than left as an example (e.g. "255")? [Measurability, Plan Error Handling Strategy] — RESOLVED: Plan Error Handling Strategy now fixes the reserved `Internal` code at `255`, frozen as part of the external reason-code contract (not an example).
- [X] CHK004 Are requirements unambiguous about whether an abort/non-unwinding fault (e.g. a `wasm32` trap or an OOM) is also required to surface as a defined error, not just unwinding panics? [Ambiguity, Spec FR-005] — RESOLVED: FR-005 now states binding-observable non-unwinding faults (e.g. recoverable allocation failure) must surface as a defined code, while a terminal host abort/`wasm32` trap is explicitly out of scope for a defined return.
- [X] CHK005 Is there a measurable acceptance criterion confirming no panic/crash crosses the boundary on any input, including malformed tokens? [Measurability, Spec SC-005] — SC-005: "No panic or crash crosses the FFI boundary on any input (including malformed tokens); every outcome is a defined return/error code."

## Parser Fuzz Entry Gate

- [X] CHK006 Is the entry-gate requirement that the parser/verify path be fuzzed and panic-free before any binding exposes it over FFI/WASM stated as a blocking precondition (not advisory)? [Completeness, Spec FR-013] — FR-013: "Before any binding exposes the verifier over the FFI/WASM boundary, the token parser/verify path MUST be fuzzed and panic-free on arbitrary input (entry gate…)" — a MUST-gated precondition.
- [X] CHK007 Are the fuzzing pass criteria measurable (what corpus, duration, or "panic-free on arbitrary input" threshold gates binding release)? [Measurability, Spec FR-013] — RESOLVED (user decision): FR-013 + plan Testing Strategy (Security tier) now define a measurable gate — committed seed corpus (valid/tampered-sig/truncated/oversized/empty/non-base64); per-PR CI runs `cargo-fuzz` ≥ 300 s with zero crashes/panics/OOMs/timeouts; findings minimized + committed as regression seeds before release; no nightly soak.
- [X] CHK008 Is it clear whether the gate is satisfied by reusing the core's fuzzed parser alone, or whether the binding glue itself must also be fuzzed before exposure? [Ambiguity, Spec FR-013] — RESOLVED: Plan Testing Strategy (Security tier) now states the gate is the core's fuzzed parser and that the thin glue adds no new parsing, so it is covered by reuse plus unit/parity tests rather than a separate fuzz target.
- [X] CHK009 Are requirements defined for what a malformed, truncated, or arbitrary input must yield across every binding (a defined error, never a crash)? [Edge-Case, Spec Edge Cases & Boundaries] — Edge Cases & Boundaries: "A malformed, truncated, or arbitrary input MUST yield a defined error, never a crash"; FR-006 makes the resulting code identical across every binding.

## Memory Safety Across the Boundary

- [X] CHK010 Do the requirements explicitly assign allocate/free ownership for every datum returned across the boundary (which side allocates, which side frees)? [Completeness, Spec FR-008] — FR-008 + AD-004 + HINT-003: callee allocates opaque handles freed via explicit `ls_*_free`; all inputs are caller-owned/borrowed.
- [X] CHK011 Are requirements stated to prevent leaks, double-free, and use-after-free, or is only "leak-free" called out while double-free/use-after-free are unaddressed? [Coverage, Spec FR-008] — RESOLVED: added FR-015 requiring double-free and use-after-free safety (defined no-op/`BadArgument`, never UB), complementing FR-008's leak-free contract.
- [X] CHK012 Is the borrowed-vs-owned status of every input (token string, pubkey bytes, fingerprint) versus every callee-allocated handle specified unambiguously? [Clarity, Plan HINT-003] — HINT-003: "Inputs (token string, pubkey bytes, fingerprint) are borrowed (caller-owned); only opaque handles are callee-allocated and MUST be freed via `ls_*_free`."
- [X] CHK013 Are requirements defined for the behavior when a host frees a handle twice or uses a handle after `ls_*_free`? [Edge-Case, Plan AD-004] — RESOLVED: FR-015 plus the new "Double-free / use-after-free" row in Plan Error Handling Strategy define the behavior as a defined no-op/`BadArgument`, never UB.

## Null / Invalid Handle Handling

- [X] CHK014 Are requirements defined for the result of passing a null or invalid handle to any boundary function (defined `BadArgument` code, no null deref)? [Completeness, Plan Error Handling Strategy] — Plan Error Handling Strategy "Null / invalid handle" row: "return `BadArgument` code; no deref of null", now backed by FR-016.
- [X] CHK015 Is the null/invalid-handle contract specified consistently across all entry points, or only for the verify call? [Consistency, Plan API Surface Summary] — RESOLVED: FR-016 states the null/invalid-handle contract "applies to every entry point that accepts a handle, not the verify call alone," matching the API Surface Summary's full function list.
- [X] CHK016 Is there a traceable requirement (FR/SC) backing the null/invalid-handle behavior, rather than it existing only in the plan's error table? [Traceability, Spec FR-005] — RESOLVED: added FR-016 so the null/invalid-handle behavior is a traceable functional requirement, not only a plan error-table entry.

## Secret / Key Material Non-Leakage

- [X] CHK017 Are requirements explicit that no key or secret material is logged or returned across the boundary, including on error paths? [Completeness, Spec FR-014] — FR-014: bindings "MUST NOT log or return key or secret material across the boundary, including on error paths."
- [X] CHK018 Is "secret material" defined precisely enough to test (does it cover private keys, raw token bytes, and intermediate crypto state, not just the keyring)? [Clarity, Spec FR-014] — RESOLVED: FR-014 now defines "key or secret material" as private/signing keys, raw keyring public-key bytes, raw token bytes, and intermediate crypto state — explicitly not limited to the keyring object.
- [X] CHK019 Is there a measurable acceptance criterion that error paths specifically are checked for secret/key leakage? [Measurability, Spec SC-007] — SC-007: "No key or secret material is logged or returned across the FFI boundary, including on error paths (FR-014)."
- [X] CHK020 Are the reason codes required to carry no sensitive detail (e.g. no key bytes, offsets, or fingerprint data embedded in the returned outcome)? [Coverage, Spec FR-006] — RESOLVED: FR-006 now requires the returned outcome to carry no sensitive detail (no key bytes, raw token bytes, buffer offsets, or fingerprint data).
- [X] CHK021 Is it unambiguous whether the version/ABI surface (`ls_abi_version`) and diagnostic strings are also constrained from exposing sensitive build or key detail? [Ambiguity, Plan AD-006] — RESOLVED: Plan Error Handling Strategy now states `ls_abi_version()` output and diagnostic strings expose only SemVer + token-format version and MUST NOT embed key material, raw token bytes, or build secrets (FR-006/FR-014/AD-006).

## Reason-Code Consistency and Information Disclosure

- [X] CHK022 Are requirements defined that the closed reason-code set maps to stable, identical codes across all bindings so the same failure cannot disclose different detail per language? [Consistency, Spec FR-006] — FR-006 + AD-003: a single `reason_code(&VerifyError) -> u32` map reused by all bindings, so the same failure yields the same reason everywhere.
- [X] CHK023 Is there a measurable cross-binding parity criterion that the same tampered token yields the same reason code in C-ABI and WASM? [Measurability, Spec SC-003] — SC-003: "the same tampered token yields the same failure reason code, in both the C-ABI and the WASM binding."
- [X] CHK024 Are the reason codes specified to distinguish failure categories without leaking exploitable detail (e.g. tampered vs. expired without revealing crypto internals)? [Edge-Case, Spec FR-006] — RESOLVED: FR-006 now requires reason codes to distinguish categories (tampered/invalid-signature vs. expired vs. malformed) without revealing crypto internals that would aid an attacker; closed code set per Plan Error Handling Strategy (0=ok, 1=malformed, … 9=fingerprint-missing).

## Single Crypto Core (No Per-Language Reimplementation)

- [X] CHK025 Is the requirement that no binding reimplements cryptography per language stated as mandatory and traceable to a security principle? [Traceability, Spec FR-004] — FR-004 ("cryptography MUST NOT be reimplemented per language") is traced to Principle III in the spec's Compliance Check and the plan's Instructions Check.
- [X] CHK026 Are requirements clear that every binding wraps the one verifier core, leaving no language-specific crypto path to be separately reviewed? [Clarity, Plan AD-003] — FR-004 + Architecture diagram (every binding `Rel(..., core, "verify")`) + AD-005 (generated, not hand-written) leave no per-language crypto path.
- [X] CHK027 Is a binding/core or token-format version mismatch required to be detectable (no silent mismatch that could verify under the wrong rules)? [Completeness, Spec FR-012] — FR-012 + AD-006: bindings track the core SemVer and token-format version and expose `ls_abi_version()` so a mismatch is detectable, not silent.

## Dependency Security Scanning of Binding Artifacts

- [X] CHK028 Are requirements defined that binding artifacts undergo dependency security scanning as a quality gate? [Completeness, Spec FR-014] — FR-014: binding artifacts "MUST meet the project quality gates — dependency security scanning … and ≥ 80% coverage"; Plan Testing Strategy lists `cargo audit` in the Security tier.
- [X] CHK029 Is the scanning requirement's pass threshold measurable (e.g. no CRITICAL vulnerabilities) rather than just "scanned"? [Measurability, Spec FR-014] — RESOLVED: FR-014 now sets the gate at "no CRITICAL-severity vulnerabilities", with the scan failing that threshold blocking binding release.
- [X] CHK030 Is it clear whether dependency scanning covers all binding outputs (cdylib, WASM package, generated bindings) or only the Rust crate? [Coverage, Plan Testing Strategy] — RESOLVED: Plan Testing Strategy (Security tier) now states scanning covers all binding outputs — Rust crate deps (`cargo audit`), the WASM/npm package deps, and the generated-binding (UniFFI) package deps — not the Rust crate alone.

## Cross-Cutting / Coverage Gaps

- [X] CHK031 Is each security edge case in "Edge Cases & Boundaries" traceable to at least one FR or SC that makes it testable? [Traceability, Spec Edge Cases & Boundaries] — RESOLVED: every edge case now maps to an FR/SC — panic/fault → FR-005/SC-005; memory ownership → FR-008; malformed input → FR-005/SC-005; version mismatch → FR-012; unsupported platform → FR-017 (newly added).
- [X] CHK032 Are requirements defined for an unsupported platform/architecture failing clearly at build/load time rather than producing an unsafe runtime state at verify time? [Edge-Case, Spec Edge Cases & Boundaries] — RESOLVED: added FR-017 requiring an unsupported platform/architecture to fail at build or load time (never at verify time) with a published supported-target matrix; mirrored in the Plan Error Handling Strategy.
- [X] CHK033 Is the offline-only constraint stated such that no binding error or fallback path may trigger a network call that could exfiltrate token or key data? [Coverage, Spec Scope] — RESOLVED: added FR-018 requiring verification and every binding error/fallback path to be strictly offline (no network call under any outcome), so no token/key/fingerprint data can be exfiltrated.
- [X] CHK034 Are the security requirements free of conflicting statements between the spec's Compliance Check and the FRs they cite (FR-005/008/014)? [Consistency, Spec Compliance Check] — Compliance Check's Security/Testing lines cite FR-005/008/014 (plus the new FR-015/016/017/018) consistently with those requirements' text; no conflicting statements found, and the cited IDs match the FR bodies.
