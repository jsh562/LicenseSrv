# API Quality Checklist: Embeddable Verifier Bindings

> Unit tests for the binding/FFI contract requirements — do they fully and unambiguously define a stable, cross-binding C-ABI / WASM / UniFFI surface, or do gaps remain? (Requirements quality only; not code behavior.)

**Created**: 2026-06-27 | **Feature**: [spec.md](../spec.md)

## C-ABI Symbol & Header Contract

- [X] CHK101 Are the exported C-ABI symbols (function names, prefixes, signatures) enumerated as a defined contract rather than left to implementation discretion? [Completeness, Spec §FR-001] — Plan §API Surface Summary enumerates `ls_keyring_new/add/free`, `ls_verify`, `ls_result_has/limit/free`, `ls_abi_version` (generated into `licensesrv.h`); Plan §Project Structure fixes the `ls_`/`Ls*` naming contract.
- [X] CHK102 Is the requirement that the C header is generated from the core (cbindgen) stated together with which header artifact is the authoritative contract a host links against? [Clarity, Spec §FR-001] — Spec §FR-001 requires a cbindgen-generated header; Plan §API Surface Summary + §Requirement Coverage Map name `src/bindings/c-abi/include/licensesrv.h` as the authoritative header the host links against.
- [X] CHK103 Is the opaque-handle versus flat-struct shape of the C-ABI specified as a requirement so the ABI surface is unambiguous to a binding author? [Ambiguity, Spec §FR-001] — Plan §AD-001 explicitly chooses opaque handles (`LsKeyring*`, `LsResult*`) + integer reason codes over flat structs, with rationale.
- [X] CHK104 Is "stable C ABI" defined with explicit symbol-stability and naming-convention criteria (e.g. `ls_` prefix, `Ls*` opaque types) rather than as an unqualified adjective? [Measurability, Spec §FR-001] — Plan §Project Structure naming conventions ("`ls_` prefix; opaque types `Ls*`"), §AD-001 (`LsKeyring*`/`LsResult*`), and §HINT-001 + Spec §FR-022 (ABI symbol set frozen as an external contract) define symbol stability concretely.

## Reason-Code Parity Across Bindings

- [X] CHK105 Is the reason-code set defined as a stable, enumerated, closed contract identical across every binding (C-ABI, WASM, UniFFI)? [Consistency, Spec §FR-006] — Spec §FR-006 ("closed reason codes MUST map to stable, identical codes across all bindings"); Plan §AD-003 + §Error Handling Strategy ("closed `VerifyError` set in fixed order, identical across all bindings").
- [X] CHK106 Does the spec require the same failure to yield the same reason code in every binding, with a single source-of-truth mapping rather than per-binding codes? [Consistency, Spec §FR-006] — Spec §FR-006 ("the same failure yields the same reason everywhere"); Plan §AD-003 mandates a single `reason_code(&VerifyError) -> u32` reused by all bindings (not per-binding).
- [X] CHK107 Is the reason code defined as a key entity with a stable cross-binding identifier, and is its integer ordering/freeze point specified as an external contract? [Completeness, Spec §FR-006] — Spec §Key Entities defines "Reason code"; Plan §HINT-001 + Spec §FR-022 freeze the reason-code integers as an external contract before any binding ships; Plan §Error Handling Strategy fixes the `VerifyError` order.
- [X] CHK108 Is cross-binding parity made measurable (same token yields same outcome and same reason code in C-ABI and WASM) rather than asserted qualitatively? [Measurability, Spec §SC-003] — Spec §SC-003 makes parity a concrete test (same valid token verifies and same tampered token yields the same reason code in both C-ABI and WASM); Plan §Testing Strategy "Cross-binding parity" tier asserts it.

## Complete Offline-Verify Surface (FR-007)

- [X] CHK109 Does the spec enumerate every required input of the verify surface — token, trusted keyring, current time, monotonic anchor, and machine fingerprint — as mandatory parameters? [Completeness, Spec §FR-007] — Spec §FR-007 lists all five inputs (token, trusted keyring, current time, monotonic anchor, machine fingerprint) as the full offline-verify surface bindings MUST expose.
- [X] CHK110 Is reading the resulting entitlements (capability/limit) defined as a required output of the verify surface for every binding? [Completeness, Spec §FR-007] — Spec §FR-007 requires bindings to "read the resulting entitlements"; §Key Entities defines Entitlement as a capability (boolean or limit); SC-001/002/006 require reading an entitlement in each binding.
- [X] CHK111 Is "offline" defined as a hard requirement (no network call on any verify path) and made independently testable per binding? [Clarity, Spec §FR-009] — Spec §FR-009 + §FR-018 make no-network a hard requirement on every path (success/failure/internal error); §SC-012 and the per-US Independent Tests (US1/US2) make it independently testable per binding.
- [X] CHK112 Are the verify-surface inputs each given a defined type/encoding expectation (e.g. token string, keyring public keys, fingerprint bytes) so binding authors interpret them identically? [Ambiguity, Spec §FR-007] — RESOLVED: added Spec §FR-021 requiring each FR-007 input to carry a defined type/encoding in the binding contract (token = UTF-8/byte string, keyring keys = raw key bytes, fingerprint = bytes, time/anchor = the core's integer time/counter values), reinforced by Plan §HINT-003.

## Memory-Ownership Contract

- [X] CHK113 Is the allocate/free ownership contract specified explicitly — which side allocates and which side frees each value returned across the boundary? [Completeness, Spec §FR-008] — Spec §FR-008 requires an explicit allocate/free contract; Plan §AD-004 + §HINT-003 specify callee allocates opaque handles freed via explicit `ls_*_free`, inputs borrowed (caller-owned).
- [X] CHK114 Is it stated which inputs are borrowed (caller-owned) versus which outputs are callee-allocated and must be released via an explicit free function? [Clarity, Spec §FR-008] — Plan §AD-004 ("inputs borrowed; callee allocates opaque handles freed via explicit `ls_*_free`") and §HINT-003 ("token string, pubkey bytes, fingerprint are borrowed; only opaque handles are callee-allocated and MUST be freed").
- [X] CHK115 Is "leak-free" defined as a verifiable requirement (e.g. every callee-allocated handle has a paired free) rather than an aspirational adjective? [Measurability, Spec §FR-008] — Spec §FR-020 makes leak-freedom verifiable (C-ABI integration test exercises allocate/verify/free and confirms by balanced accounting or a leak sanitizer; SC-009); Plan §AD-004 pairs every callee handle with `ls_*_free`.

## Error Model (Codes, Not Panics)

- [X] CHK116 Does the spec require that no panic or undefined behavior crosses the FFI boundary, with every outcome surfaced as a defined return/error code? [Completeness, Spec §FR-005] — Spec §FR-005 (no panic/UB crosses the boundary on any surface; every outcome a defined code) + §SC-005; Plan §AD-002 wraps every `extern "C"` entry in `catch_unwind` returning a defined code.
- [X] CHK117 Are the boundary error conditions enumerated (malformed/truncated/arbitrary input, null/invalid handle, internal fault) each mapped to a defined code rather than a crash? [Edge-Case, Spec §Edge Cases] — Spec §Edge Cases + §FR-016 (null/invalid handle → `BadArgument`) and Plan §Error Handling Strategy table map each: verify failure → code (malformed/truncated), null/invalid handle → `BadArgument`, panic inside core → reserved `Internal` (255).
- [X] CHK118 Is the requirement that no key or secret material is logged or returned across the boundary stated as covering error paths as well as success paths? [Coverage, Spec §FR-014] — Spec §FR-014 forbids logging/returning key or secret material "including on error paths" (with a defined scope of "key or secret material"); §FR-006 bars sensitive detail in the returned outcome; §SC-007 asserts it.

## Version & Token-Format Mismatch Detection

- [X] CHK119 Does the spec require binding versions to track both the core's semantic version and the token-format version so a mismatch is detectable rather than silent? [Completeness, Spec §FR-012] — Spec §FR-012 requires binding versions to track both the core's semantic version and the token-format version so a binding/core mismatch is detectable, not silent.
- [X] CHK120 Is a means to detect a binding/core or token-format mismatch defined as part of the API surface (e.g. a queryable ABI/version value) rather than implied? [Clarity, Spec §FR-012] — Plan §AD-006 + §API Surface Summary expose `ls_abi_version()` (embedding core SemVer + token-format version); Spec §FR-022 makes the queryable value an explicit part of the contract.
- [X] CHK121 Is "detectable, not silent" made measurable — is it specified at what point (build/load/verify) and how a mismatch surfaces to the host? [Measurability, Spec §Edge Cases] — RESOLVED: added Spec §FR-022 pinning the surface point (host-queryable version value, e.g. `ls_abi_version()`, surfaces a mismatch at library load/initialization before any verify) and §SC-011 makes it testable; consistent with Plan §AD-006 and §Error Handling Strategy.

## Packaging & Distribution Per Target

- [X] CHK122 Are the distribution artifacts per target defined (native shared library + header; package-manager-installable WASM package) as concrete deliverables? [Completeness, Spec §FR-010] — Spec §FR-010 names a native shared library + header and a package-manager-installable WASM package; Plan §Requirement Coverage Map (FR-010) ties them to `src/bindings/{c-abi,wasm}/`; §SC-010 asserts each ships.
- [X] CHK123 Is the supported platform/architecture target matrix defined, and is the requirement that an unsupported platform fails clearly at build/load time (not verify time) stated? [Edge-Case, Spec §Edge Cases] — Spec §FR-017 + §Edge Cases require fail-at-build/load (not verify) and a published target matrix; Plan §Technical Context defines the matrix (native `x86_64`/`aarch64`, `wasm32-unknown-unknown`, UniFFI targets) and §Risk Mitigation publishes it with per-target CI.
- [X] CHK124 Is each primary binding's reference integration required to demonstrate offline verification with no network call, and is the sample's pass condition defined? [Coverage, Spec §FR-009] — Spec §FR-009 requires a reference integration per primary binding demonstrating offline verify; the US1/US2 Independent Tests + §SC-012 define the pass condition (valid token verifies offline, tampered/expired rejected); Plan §Testing Strategy (Integration C / WASM) encodes it.

## Quickstart & Developer Experience

- [X] CHK125 Is the first-successful-offline-verify target quantified (under 30 minutes) and tied to a defined quickstart artifact? [Measurability, Spec §FR-011] — Spec §FR-011 + §SC-004 quantify the target (< 30 min to first successful offline verify); Plan §Requirement Coverage Map (FR-011) ties it to the quickstart artifact `src/bindings/README.md`.

## ABI Backward-Compatibility / SemVer

- [X] CHK127 Does the spec require the reason-code integers and ABI symbols to be frozen as an external contract before any binding ships, so later changes follow versioning rules? [Consistency, Spec §FR-012] — RESOLVED: added Spec §FR-022 requiring both the reason-code integers and the exported ABI symbol set to be frozen as an external contract before any binding ships, with later changes governed by versioning rules; reinforces Plan §HINT-001.
- [X] CHK128 Is the relationship between binding SemVer and the core/token-format version specified clearly enough to govern what constitutes a breaking ABI change? [Clarity, Spec §FR-012] — RESOLVED: Spec §FR-022 now defines the rule — any change to a frozen reason-code integer or exported ABI symbol is a breaking ABI change requiring a binding major-version bump, while backward-compatible additions follow the binding's SemVer tracking of the core/token-format version (FR-012).

## Cross-Cutting Contract Integrity

- [X] CHK132 Does every functional requirement for the binding API trace to at least one user story and one measurable success criterion? [Traceability, Spec §Success Criteria] — RESOLVED: added Spec §SC-009 (memory FR-008/015/016/020), §SC-010 (packaging/platform FR-010/017), §SC-011 (version mismatch FR-012/022), and §SC-012 (offline error paths FR-018/009), so every binding FR now traces to a user story and a measurable success criterion (the remaining FRs already mapped via SC-001..SC-008).
- [X] CHK133 Is the single-core constraint (no per-language crypto reimplementation) stated unambiguously enough to bound what each binding may and may not contain? [Ambiguity, Spec §FR-004] — Spec §FR-004 ("Every binding MUST wrap the single Rust verifier core; cryptography MUST NOT be reimplemented per language"); Plan §Constraints + §AD-005 reinforce one core, no hand-written/per-language crypto.
- [X] CHK134 Is the fuzz-before-FFI entry gate defined as a prerequisite condition on exposing any binding surface, with a clear pass criterion (panic-free on arbitrary input)? [Completeness, Spec §FR-013] — Spec §FR-013 makes it an entry gate ("Before any binding exposes the verifier over the FFI/WASM boundary, the token parser/verify path MUST be fuzzed and panic-free on arbitrary input"); §SC-007 asserts the parser is fuzzed before any binding ships; Plan §Testing Strategy (Security: cargo-fuzz) encodes it.
- [X] CHK135 Are the key entities the API surfaces (license token, keyring, entitlement, reason code) defined consistently between the spec and the contract they cross the boundary as? [Consistency, Spec §Key Entities] — Spec §Key Entities defines license token (`LIC1`), keyring, entitlement, reason code; Plan §Data Model Summary maps them to the core's in-memory types surfaced across the boundary, and §API Surface Summary surfaces them as `LsKeyring*`/`LsResult*` + integer reason codes — consistent.
- [X] CHK136 Is the ≥80% coverage quality gate for the binding glue stated as a measurable acceptance condition for the API artifacts? [Measurability, Spec §FR-014] — Spec §FR-014 states a measurable gate (≥ 80% coverage of the binding glue + dependency security scan with a no-CRITICAL threshold that blocks release); Plan §Testing Strategy (Coverage: cargo-llvm-cov ≥ 80%) operationalizes it.
