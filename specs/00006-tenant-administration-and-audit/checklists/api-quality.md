# API Quality Checklist: Tenant Administration and Audit (E005 Admin Console REST Surface)

*A "unit test for the spec": each item interrogates whether the admin `/admin` REST requirements and OpenAPI contract are complete, clear, and consistent — it does not test running code.*

**Created**: 2026-07-02 | **Feature**: [spec.md](../spec.md) | **Contract**: [admin-api.openapi.yaml](../contracts/admin-api.openapi.yaml)

## Endpoint Contract Completeness

- [X] CHK101 Does the contract define a request schema (where a body applies) and a response schema for every one of the 11 operations, including the bodiless logout/rotate/revoke operations? [Completeness, contracts §paths] — contracts §paths: all 11 operationIds define a response schema, and every body-bearing op (login, createUser, updateUser, createApiKey) a requestBody; the bodiless ops resolve to logout→204+Set-Cookie, rotate→ApiKeySecret, revoke→ApiKeyMetadata.
- [X] CHK102 Does each operation enumerate every applicable status code (its 2xx plus each reachable 4xx), so no error outcome named in the Plan's Error Handling Strategy is absent from an operation's `responses`? [Coverage, contracts §paths + Plan §Error Handling Strategy] — every op's `responses` list its 2xx + reachable 4xx; the Plan §Error Handling Strategy codes (400/401/403/404/409/429) each appear on the op(s) that can raise them (e.g. 429 only on login; 404 only on the {id} ops).

## Authentication & Session Scheme

- [X] CHK103 Is the `sessionCookie` scheme (apiKey / in:cookie / name:admin_session) fully defined and explicitly distinguished from the machine `X-API-Key` header, and is `POST /admin/auth/login` documented as the ONLY operation overriding the global requirement with `security: []`? [Clarity, contracts §components.securitySchemes + §security + Plan §Summary] — §securitySchemes.sessionCookie (apiKey/in:cookie/name:admin_session) states "HUMAN session credential (NOT the machine `X-API-Key`)"; global `security: [sessionCookie]`; login is the sole `security: []` override, stated in §description and the login op.
- [X] CHK104 Are the required cookie attributes (HttpOnly, Secure, SameSite=Strict, Path=/admin, bounded Max-Age) specified, and is the bounded session TTL given a concrete measurable value rather than a `<ttl>` placeholder? [Measurability, contracts §securitySchemes + Spec FR-003] — RESOLVED: replaced the `Max-Age=<ttl>` placeholder with the concrete bounded TTL `3600` s (1 h) in the login Set-Cookie header description + §securitySchemes (+ README Auth-model); all five attributes now specified with a measurable value.
- [X] CHK105 Does `LoginRequest` include the `tenantSlug` selector that AD-001/HINT-002 require to disambiguate an email that may exist in multiple tenants, or does the email+password-only body contradict the Plan's `{tenantSlug,email,password}`? [Consistency, contracts §LoginRequest vs Plan §AD-001 + §API Surface Summary] — RESOLVED: added required `tenantSlug` (minLength 1) to §LoginRequest, updated the `standard` login example to `{tenantSlug,email,password}`, and noted the tenant selector in README Auth-model — now consistent with Plan AD-001/HINT-002.

## RBAC Authorization

- [X] CHK106 Does every authenticated operation carry an explicit `x-rbac.minRole` whose value matches the Plan's API Surface Summary and README RBAC table, and is the `owner > admin > viewer` ordering stated once so satisfaction of each `minRole` is unambiguous? [Consistency, contracts §x-rbac + §Role vs Plan §API Surface Summary] — every authenticated op has x-rbac.minRole (viewer: logout/me/listUsers/audit; admin: create/updateUser + all api-key ops) matching Plan §API Surface Summary and README RBAC table; ordering `owner > admin > viewer` stated in §description and §Role.
- [X] CHK107 Does the contract tie a `403 forbidden` (RBAC denial) to being recorded as an auditable security event, keeping the contract traceable to Spec FR-004/FR-005? [Traceability, contracts §responses.Forbidden + Spec FR-005] — §responses.Forbidden: "Denied fail-closed and recorded as an auditable security event (FR-004/005)".

## Error Model

- [X] CHK108 Does the `Error.code` enum contain exactly the codes the operations and README reference (validation_error, unauthenticated, forbidden, not_found, last_owner, already_revoked, email_exists, rate_limited), with no operation returning a code absent from the enum and no enum member left unreachable? [Consistency, contracts §Error.code enum vs §responses] — RESOLVED: removed the unreachable generic `conflict` member from §Error.code (no operation nor the README referenced it), so the enum now equals exactly the 8 codes used — no missing and no unreachable member.
- [X] CHK109 Does the 429 response require a `Retry-After` header, and is 429 `rate_limited` scoped only to the login path per FR-018? [Completeness, contracts §responses.RateLimited + Spec FR-018] — RESOLVED: marked the §responses.RateLimited `Retry-After` header `required: true`; 429 is listed only on `POST /admin/auth/login`, consistent with FR-018.
- [X] CHK110 Are the three distinct 409 conditions (last_owner, already_revoked, email_exists) each mapped to the specific operation(s) that can raise them, so their triggering conditions are unambiguous? [Clarity, contracts §/admin/users + §/admin/api-keys + Plan §Error Handling Strategy] — last_owner → updateUser (PATCH /admin/users/{userId}); already_revoked → rotate + revoke; email_exists → createUser; each 409 is defined only on its raising op.

## Secrecy Invariants

- [X] CHK111 Does the contract guarantee, across every response schema, header, and example, that no human password, password hash, or raw session token appears (password `writeOnly`; token delivered only via `Set-Cookie`)? [Consistency, contracts §LoginRequest + §securitySchemes + Spec FR-017] — §LoginRequest.password is `writeOnly`; no response schema/example carries a password or hash; the opaque session token appears only in the `Set-Cookie` header (§securitySchemes: "never returned in any response body (FR-017)").
- [X] CHK112 Is the API-key `secret` confined to the dedicated `ApiKeySecret` schema used solely by create and rotate, with list and revoke using `ApiKeyMetadata` (no `secret` field), and does the contract state `ApiKeySecret` MUST NOT be used by any read/list endpoint? [Consistency, contracts §ApiKeySecret + §ApiKeyMetadata + Spec FR-009] — `secret` lives only on §ApiKeySecret (createApiKey 201 + rotate 200); listApiKeys/revoke use §ApiKeyMetadata (no `secret`); §ApiKeySecret states it "MUST NOT be used by any read/list endpoint" (FR-009).

## Audit Surface (Read-Only)

- [X] CHK113 Does the contract establish the audit surface as strictly read-only — a single `GET /admin/audit` with `x-append-only: true` and no create/update/delete operation anywhere in the document — consistent with FR-013? [Coverage, contracts §/admin/audit + Spec FR-013] — `/admin/audit` exposes only GET with `x-append-only: true` and description "STRICTLY READ-ONLY... no create, update, or delete operation anywhere"; no mutating verb on audit exists (FR-013).
- [X] CHK114 Are all four audit filters (from, to, securityEvent, actor) plus cursor pagination (cursor/nextCursor/limit) defined with unambiguous semantics, including from-inclusive vs to-exclusive bounds and the limit default/max? [Clarity, contracts §/admin/audit.parameters + Spec FR-012] — from = inclusive lower bound, to = exclusive upper bound, securityEvent (boolean), actor, plus cursor + nextCursor and limit (min 1, max 200, default 50) all defined (FR-012).
- [X] CHK115 Is the `actor` audit filter's matching semantics unambiguous — exact match vs substring, and whether it accepts a user id, an email, and an api-key id interchangeably? [Ambiguity, contracts §/admin/audit.actor] — RESOLVED: clarified §/admin/audit.actor as an EXACT, case-sensitive, whole-value (non-substring/prefix) match against the entry's recorded actor identifier — a user id, email, or api-key id, whichever form the entry stored.

## Tenant Scoping & Conventions

- [X] CHK116 Does the contract assert that every path is tenant-scoped from the session with NO tenant path or query parameter, so a caller can never widen scope (FR-002)? [Completeness, contracts §description + Spec FR-002] — §description (TENANT SCOPING): "Every endpoint is implicitly scoped to the session's tenant (FR-002). There is no tenant path/query parameter... can never be widened by the caller"; no path/query tenant parameter exists anywhere.
- [X] CHK117 Does the `UserStatus` enum (invited, active, deactivated) reconcile with the Plan data-model's `app_user.status CHECK(active/deactivated)`, which omits `invited`? [Consistency, contracts §UserStatus vs Plan §Data Model Summary] — RESOLVED: added a reconciliation note to §UserStatus (+ README Conventions) mapping `invited` → a NULL `app_user.password_hash` and recording that the data-model status domain is reconciled to include `invited` (the Data-Integrity evaluator adds `invited` to the data-model CHECK), so contract and schema agree.
- [X] CHK118 Does the contract specify the double-submit `X-CSRF-Token` header requirement on state-changing (POST/PATCH) `/admin` operations required by AD-006/HINT-005, or does it under-specify CSRF defense by relying on SameSite alone? [Completeness, contracts §paths vs Plan §AD-006 + §HINT-005] — RESOLVED: added a required `components.parameters.CsrfToken` (`X-CSRF-Token` header) referenced by all six state-changing POST/PATCH ops (logout, createUser, updateUser, createApiKey, rotate, revoke — not login/GETs), and corrected §securitySchemes + README to state SameSite=Strict is necessary but NOT sufficient, paired with the double-submit token (AD-006/HINT-005).
- [X] CHK119 Is the camelCase field-naming convention documented, including its deliberate divergence from the snake_case machine contracts and the snake_case error `code` values, so the boundary is explicit? [Clarity, contracts §description + README §Conventions + Plan §AD-007] — RESOLVED: §description already documents camelCase vs snake_case machine contracts; added to README §Conventions the deliberate intra-API exception that error `code` enum values are snake_case machine tokens (opaque identifiers, not field names), making the boundary explicit.
- [X] CHK120 Does the contract define behavior for boundary inputs such as an `UpdateUserRequest` with neither field (minProperties:1), a `CreateApiKeyRequest` with an empty scopes array (minItems:1), and an exhausted audit page (nextCursor:null)? [Edge-Case, contracts §UpdateUserRequest + §CreateApiKeyRequest + §AuditList] — §UpdateUserRequest `minProperties: 1`, §CreateApiKeyRequest `scopes.minItems: 1`, §AuditList `nextCursor` typed `[string,"null"]` with example `nextCursor: null` on the exhausted page.
