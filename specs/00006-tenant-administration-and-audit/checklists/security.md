# Security Requirements Quality Checklist: Tenant Administration and Audit

*A "unit test" for the E005 security requirements — each item probes whether the spec/plan/contracts are complete, clear, and consistent about session, credential, RBAC, tenant-isolation, and audit security, not whether code behaves.*

**Created**: 2026-07-02 | **Feature**: [spec.md](../spec.md)

## Session Security & Cookie Handling

- [X] CHK001 Are the session-cookie protection attributes (HttpOnly + Secure + SameSite) stated as a normative, testable requirement rather than appearing only as a contract example/description? [Completeness, Plan HINT-001 / contracts sessionCookie] — RESOLVED: promoted the cookie attributes from a plan hint/contract description to a normative spec requirement — FR-003 now MUSTs the token be delivered "only via a cookie set `HttpOnly`, `Secure`, and `SameSite` (Strict)" (§Requirements), consistent with plan HINT-001/AD-003 and the contract sessionCookie scheme.
- [X] CHK002 Is the "bounded period" for session expiry quantified as a concrete value or upper bound, or is it left unmeasurable? [Measurability, Spec FR-003] — RESOLVED: FR-003 (§Requirements) now bounds expiry measurably — "expire after a bounded, operator-configurable window (default ≤ 24 hours)" — and the Compliance Check §Security Requirements bullet echoes it, replacing the unmeasurable "bounded period".
- [X] CHK003 Do the requirements state that the raw session token is never stored (only its hash) and never appears in any response body, header aside from Set-Cookie? [Completeness, Spec FR-017 / data-model §3] — RESOLVED: FR-003 (§Requirements) now MUSTs the token "stored server-side only as a one-way hash — the raw token is never persisted, logged, or returned in any response body or header other than the `Set-Cookie` issued at sign-in", promoting to the spec what data-model §3/§10 (token_hash never returned; raw token only in Set-Cookie) already carried.
- [X] CHK004 Is there a requirement defining the timing by which a revoked or expired session is rejected — immediately on the next request vs. eventually? [Edge-Case, Spec FR-003 / data-model §11] — RESOLVED: FR-003 (§Requirements) now fixes the timing — "rejected on the next request once expired or revoked" — matching data-model §11 ("effective for the next request"), removing the "eventually" ambiguity.
- [X] CHK005 Are requirements defined for what happens to an already-active session when its user is deactivated (owner-status gate on next request vs. eager revocation), and are FR-007 and the data-model §11 wording consistent on this? [Consistency, Spec FR-007 / data-model §11] — Covered: FR-007 (§Requirements) "unable to sign in or perform actions on subsequent requests" is consistent with data-model §3/§11 ("valid iff … owner.status='active'"; "invalidates all their sessions on the next request (owner-status gate; sessions may also be revoked eagerly)") — both specify next-request effect via the owner-status gate, with eager revocation as an allowed option.

## Credential Secrecy & Password Storage

- [X] CHK006 Do the requirements mandate that the password be stored only as a slow-KDF (scrypt/argon2) hash, and is the distinction from the deliberately fast session-token hash stated so neither is confused for the other? [Clarity, Spec FR-017 / data-model §3] — Covered: FR-017 mandates salted one-way hashing; data-model §2/§3 make the slow-vs-fast distinction explicit — password_hash is a "Slow-KDF one-way hash (scrypt/argon2)" while token_hash is "a fast hash (SHA-256 …) … a slow KDF is unnecessary (contrast password_hash, which MUST be slow-KDF)" — and plan AD-002 (scrypt) / AD-003 (SHA-256 token_hash) confirm it.
- [X] CHK007 Is "never logged or returned" scoped to include audit `before`/`after` snapshots and error `details`, so no credential/hash/token can leak through those channels? [Completeness, Spec FR-017 / data-model §10] — Covered: FR-017 bars any log/return of the credential; data-model §10 explicitly closes the audit channel ("`before`/`after` snapshots MUST be PII/secret-minimized at write time — never snapshot a password, token, or key hash") and §12 repeats it; the contract `Error` schema closes the error channel ("`details` … MUST NOT contain a password, hash, session token, or API-key secret").

## Brute-Force Resistance & Login Hygiene

- [X] CHK008 Are the lockout/throttle threshold (N failed attempts) and the lockout duration/backoff specified as measurable requirements rather than deferred entirely to implementation? [Measurability, Spec FR-018 / Plan AD-005] — RESOLVED: FR-018 (§Requirements) now names measurable bounds — "after a bounded, operator-configurable number of consecutive failed attempts (default 5) the account MUST be locked out for a bounded, operator-configurable window" — turning plan AD-005's abstract "N failures → timed lockout" into a testable, operator-tunable requirement.
- [X] CHK009 Is it unambiguous whether brute-force protection is per-account, per-IP, or both, and how that choice interacts with the no-enumeration rule? [Ambiguity, Spec FR-018 / Plan AD-005] — Covered: plan AD-005 fixes it to per-account ("per-user `failed_login_count` + `locked_until` on `app_user`") and data-model §9 implements it on the two per-user columns; the interaction with no-enumeration is spelled out in §9 — locked/deactivated/unknown-email/wrong-password all return "the same generic failure … the distinction lives only in the audit trail."
- [X] CHK010 Is it required that throttle/lockout events be recorded as auditable security events (security_event flag set)? [Traceability, Spec FR-018 / data-model §12] — Covered: FR-018 requires lockout/throttle events be auditable; data-model §9 and the §12 audit table map them to `auth.login_locked` / `auth.login_throttled` with `security_event = true`, so the flag is required, not optional.
- [X] CHK011 Is there an explicit requirement that a failed sign-in returns a response indistinguishable across unknown tenant, unknown email, wrong password, locked, and deactivated cases (no user enumeration)? [Completeness, Plan HINT-002 / data-model §9] — Covered: data-model §9 states "the same generic failure is returned to the client whether the email/tenant is unknown, the password is wrong, the account is locked, or the user is deactivated" (enumerating exactly these cases); plan HINT-002 ("Return a generic error for bad tenant/email/password alike (no user enumeration)") and the contract login `401` ("Generic code/message to avoid account enumeration") reinforce it.

## CSRF Protection

- [X] CHK012 Is CSRF protection for cookie-authenticated mutations captured as an actual requirement, given the plan mandates it (AD-006) but no spec FR names CSRF — is the source of authority traceable? [Traceability, Plan AD-006] — RESOLVED: added FR-019 (§Requirements) giving CSRF a spec home — "Cookie-authenticated state-changing requests MUST be protected against cross-site request forgery (CSRF): … `SameSite` (Strict) … plus … a validated double-submit CSRF token (`X-CSRF-Token`)" — so plan AD-006/HINT-005 now trace up to an authoritative FR, and the Compliance Check §Security Requirements bullet cites FR-019.
- [X] CHK013 Do the artifacts agree on the required CSRF defense — the contract calls SameSite=Strict "the primary CSRF mitigation" while the plan requires an additional double-submit `X-CSRF-Token` on every state-changing request — or is this an unreconciled inconsistency? [Consistency, contracts sessionCookie / Plan AD-006 / HINT-005] — RESOLVED: new FR-019 (§Requirements) reconciles the two by making BOTH controls authoritative — SameSite (Strict) is "necessary but not sufficient on its own" (so "primary" ≠ "only") AND a double-submit `X-CSRF-Token` is additionally required — matching plan AD-006/HINT-005. The contract wording refinement (naming the double-submit token in sessionCookie) is owned by the API-Quality evaluator over `contracts/`.

## RBAC & Fail-Closed Authorization

- [X] CHK014 Are requirements explicit that RBAC is enforced server-side and fail-closed (deny-by-default) on every privileged action, including admin surfaces later plugged into the console shell (so a plug-in cannot weaken it)? [Completeness, Spec FR-004 / FR-015] — Covered: FR-004 "enforce role-based access control on every privileged action server-side, failing closed (deny by default)"; FR-015 requires plugged-in surfaces to inherit the shell "without weakening tenant scoping or RBAC"; SC-010 makes it testable (a plugged-in surface "cannot read or act outside the tenant or above the user's role"), and plan AD-004 places enforcement in a server-side fail-closed preHandler.
- [X] CHK015 Is every denied action required to be recorded as an auditable security event, and is the authoritative role hierarchy (owner > admin > viewer) defined in the spec rather than only in the plan/contract? [Traceability, Spec FR-005 / contracts RBAC] — RESOLVED: FR-005 already requires every denial be "recorded as an auditable security event"; firmed the previously hedged role list ("e.g. owner, admin, viewer") in Key Entities §Role to the authoritative closed, ordered set — "a fixed, ordered, closed set — owner > admin > viewer … no other roles exist" — so the hierarchy now lives in the spec, matching the contract/plan `owner > admin > viewer`.

## Tenant Isolation & Session Scoping

- [X] CHK016 Do the requirements state that a session is bound to exactly one tenant with no caller-controllable path (path/query/header) to widen scope to another tenant? [Coverage, Spec FR-002 / contracts tenant scoping] — Covered: FR-001 binds a session to "exactly one tenant"; FR-002 scopes every read/write to it with "a session MUST NOT access another tenant's data under any circumstance" (SC-002 makes it testable); the contract states "There is no tenant path/query parameter — the tenant is resolved from the session and can never be widened by the caller", and data-model §3/§4 enforce it via the RLS predicate and per-request tenant resolution.
- [X] CHK017 Is the privileged (RLS-bypassing) pre-tenant session-token lookup constrained by requirement so it reads only the row needed to resolve the tenant and can never become a general cross-tenant read path? [Edge-Case, data-model §4 / §6] — Covered: data-model §4 constrains the lookup — "reads only the row needed to resolve `(tenant_id, user_id)` and validity; it never returns `token_hash` and does nothing tenant-scoped. This is the one legitimate cross-tenant read for sessions" — and §6 bounds it to the sanctioned `resolveApiKey` bootstrap on the privileged connection, immediately dropping to `withTenant` scope thereafter.

## Privilege & Key Lifecycle Safeguards

- [X] CHK018 Do the requirements address the last-owner safeguard's concurrency edge case (two simultaneous demotions/deactivations jointly stranding the tenant) and clarify that it counts only owners whose users are active? [Edge-Case, Spec FR-008 / data-model §7] — Covered: data-model §7 addresses both — the active-owner qualifier ("assert ≥ 1 other `active`-user owner remains") and the race ("two simultaneous demotions could each pass a naive count and jointly strand the tenant. Guard with row-locking (`SELECT … FOR UPDATE`) or a `SERIALIZABLE` transaction … Also treat deactivating the last active owner as covered"); plan AD-008/HINT-003 mandate the same-transaction FOR-UPDATE guard.
- [X] CHK019 Are requirements explicit that the API-key secret appears in exactly one response (create/rotate) and is never retrievable afterward, and that a rotated/revoked key stops authenticating immediately? [Completeness, Spec FR-009 / FR-010] — Covered: FR-009 "the secret MUST be shown only once at creation and never be retrievable thereafter"; FR-010 "a rotated/revoked key MUST stop authenticating"; the contract confines `secret` to the `ApiKeySecret` schema used solely by create + rotate (every read/list/revoke uses `ApiKeyMetadata` with no secret) and states revoke "immediately stops authenticating"; data-model §8/§10 reinforce (secret shown once, `key_hash` never re-projected).

## Audit Integrity

- [X] CHK020 Is "append-only and tamper-evident" defined at a mechanism-independent level (no create/update/delete by any role including owner) with the meaning of "tamper-evident" clarified (grant-level immutability vs. cryptographic evidence), and is the audit write required to be atomic with its mutation so no mutation escapes the trail? [Ambiguity, Spec FR-013 / FR-014 / data-model §12] — RESOLVED: FR-013 (§Requirements) now disambiguates the term — "'tamper-evident' means append-only immutability enforced at the privilege/grant layer … rather than cryptographic hash-chaining" — and FR-014 now requires the audit write "in the same transaction as the mutation (atomic — if the audit write fails, the mutation is rolled back) so no mutation escapes the trail", matching data-model §12 (INSERT/SELECT-only grant; same-transaction atomic append).
